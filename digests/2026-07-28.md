## 1. MCP仕様 2026-07-28リリース候補: ステートレス化・Tasks正式化・認可強化を含む最大級の改訂

**タイトル:** The 2026-07-28 MCP Specification Release Candidate
**情報源:** [Model Context Protocol公式ブログ](https://blog.modelcontextprotocol.io/posts/2026-07-28-release-candidate/)（直接WebFetchで確認）、[The Register](https://www.theregister.com/devops/2026/07/23/model-context-protocol-prepares-to-break-with-its-stateful-past/5276722)、[TechCrunch](https://techcrunch.com/2026/07/20/ais-most-important-protocol-is-getting-a-little-bit-easier-to-use/)

**何が新しいか:**
MCP(Model Context Protocol)の次期仕様が2026-07-28付でリリース候補から正式版へ移行する。最大の変更はプロトコルレベルのセッション概念を完全に廃止し、すべてのリクエストを自己完結させる「ステートレス化」。従来必要だった`Mcp-Session-Id`ヘッダーによるスティッキールーティングや共有セッションストアが不要になり、単純なラウンドロビン型ロードバランサーの背後でリモートMCPサーバーを動かせるようになる。

**技術的なポイント:**
- `initialize`/`initialized`ハンドシェイクを廃止し、クライアント情報は各リクエストの`_meta`メタデータで運ばれるようになる。
- サーバー→クライアントの長時間処理は、サーバーが`InputRequiredResult`を返してクライアントが再試行する形の「Multi-Round-Trip Requests」パターンに置き換わり、どのサーバーインスタンスでも再試行を処理できる設計になっている。
- 実験的機能だった「Tasks」が正式な拡張機能に昇格し、`tools/call`がタスクハンドルを返し、クライアントは`tasks/get`・`tasks/update`・`tasks/cancel`で進捗を駆動する形に変更(`tasks/list`は廃止)。新たに「MCP Apps」拡張も追加され、サーバーがサンドボックス化されたiframe内にHTML UIを配信できるようになる。
- 認可周りはOAuth 2.0/OpenID Connectとの整合を強める6件の拡張提案が入り、`iss`パラメータのRFC 9207準拠検証や`application_type`の登録時宣言などが必須化される。Python・TypeScript・Go・C#の各SDKでベータ版が提供済み(Python v2では`FastMCP`が`MCPServer`に改称)。「Roots」「Sampling」「Logging」は非推奨化され、廃止まで最低12ヶ月の猶予期間が設けられる。

**なぜ重要か:**
MCPサーバーを本番運用している、またはこれから運用するエンジニアにとって、非互換変更を含むこの改訂への追従は避けて通れない対応。ステートレス化はスケーラビリティ面で明確な利点がある一方、既存実装の書き換えコストも発生する。FDE的にMCPベースの顧客向けエージェント基盤を設計・移行支援する立場では、このリリースノートの内容そのものが実務知識になる。

**リンク:** https://blog.modelcontextprotocol.io/posts/2026-07-28-release-candidate/

## 2. Moonshot AI、2.8兆パラメータのオープンウェイトモデル「Kimi K3」を公開

**タイトル:** Kimi K3 open weights release
**情報源:** [VentureBeat](https://venturebeat.com/technology/chinas-moonshot-ai-releases-kimi-k3-the-largest-open-source-model-ever-rivaling-top-u-s-systems)、[Tom's Hardware](https://www.tomshardware.com/tech-industry/artificial-intelligence/moonshot-ai-releases-weights-for-kimi-k3-firing-a-shot-across-the-bow-of-openai-and-anthropic-open-weight-model-performs-almost-as-well-as-frontier-models-while-being-2-3x-easier-to-run)、[OpenRouter](https://openrouter.ai/moonshotai/kimi-k3)（2026年7月26日）

**何が新しいか:**
中国Moonshot AIが、当初予告の7月27日より1日早い7月26日、2.8兆パラメータのオープンウェイトモデル「Kimi K3」を無料公開した。3兆パラメータ級として初のオープンソースモデルとされ、トークンあたりの実活性化パラメータは約1042億(896エキスパート中16エキスパートを活性化、約1.8%)にとどまるMoE構成。

**技術的なポイント:**
- アーキテクチャは「Kimi Delta Attention (KDA)」と「Attention Residuals (AttnRes)」を採用し、ネイティブなビジョン対応と100万トークンのコンテキストウィンドウを持つ。
- 重みはMXFP4量子化で配布されており、フルウェイトのサイズは約1.4テラバイトで自前ホスティングには相当なハードウェアが必要になる。
- ベンチマークでは、実世界タスクを44職種・9業界で測るGDPval-AA v2でスコア1,687を記録し、Claude Fable 5 Max(1,815)・GPT-5.6 Sol Max(1,747.8)に次ぐ3位。一方、Arena.aiのFrontend Code Arenaでは1,679 Eloで全モデル中1位となり、Claude Fable 5(1,631)を上回った。

**なぜ重要か:**
フロンティア級に近い性能を持つモデルが無料でセルフホスト可能になったことは、コスト制約のある環境でのエージェント開発や、データを外部に出せない顧客向け導入(オンプレ/プライベートクラウド)の選択肢を広げる。FDEとして顧客のインフラ制約に合わせたモデル選定を提案する際の重要な比較対象になる。

**リンク:** https://venturebeat.com/technology/chinas-moonshot-ai-releases-kimi-k3-the-largest-open-source-model-ever-rivaling-top-u-s-systems

## 3. エージェントベンチマークの「部分実行」はどこまで信頼できるか — SWE-bench/AppWorld/tau-benchのリプレイ分析

**タイトル:** How Many Tasks Are Enough for Agent Benchmark Decisions? A Replay Analysis of Public LLM Agent Benchmarks（邦題: エージェントベンチマークの意思決定に十分なタスク数は？公開LLMエージェントベンチマークのリプレイ分析）
**情報源:** [arXiv:2607.12338](https://arxiv.org/abs/2607.12338)（2026年7月14日投稿、著者: Wei-Jung Huang）

**何が新しいか:**
SWE-benchやAppWorld、tau-benchのようなエージェントベンチマークは全タスクを実行すると高コストなため、部分実行で済ませたくなる場面が多い。しかし「タスクの何割を実行したか」という比率だけでは、その部分実行結果が全タスク実行時と同じ優劣判定を支持するかどうかは分からない。本研究は公開されているタスク単位の実測記録をリプレイ分析することで、この問いに定量的に答えている。

**技術的なポイント:**
- 「十分な予算」の定義として、(1) 全タスク実行時の意思決定と同じ結論を支持すること、(2) 必須タスクグループを網羅すること、(3) 未解決の比較が目標割合以下に収まること、の3条件を設定。
- 5パーセントポイント刻みの予算グリッドで、厳格な閾値(0パーセントポイント)のもとで各ベンチマークが全条件を満たし始める最小予算割合を算出した結果、AppWorldは15%、tau-benchは25%、SWE-bench Verifiedは90%で条件を満たし始めることが分かった。
- ベンチマークによって「十分な部分実行の割合」が大きく異なる(15%〜90%)ことを定量的に示した点が本研究の核心であり、単純な固定割合(例: 「常に30%でよい」)のヒューリスティックが誤った意思決定につながりうることを裏付けている。

**なぜ重要か:**
自社エージェントの評価・CI回帰テストを設計する際、「どのベンチマークをどこまで走らせれば十分な確度で判断できるか」は評価コストと信頼性のトレードオフに直結する実務課題。特にSWE-bench Verifiedのように高い割合(90%)が必要なベンチマークをむやみに部分実行で済ませると誤判定のリスクが高いことを示しており、評価パイプラインを設計・顧客に説明するFDE的な仕事にそのまま応用できる知見。

**リンク:** https://arxiv.org/abs/2607.12338
